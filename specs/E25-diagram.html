Testimonial agent

Architecture of the feature

A visitor submits a photo and a few words by talking to an agent. One durable workflow run carries each submission from its first message to the editor’s decision, days later if need be. The model proposes and checks; code decides what enters the draft; an editor decides what is published. This page is the picture; the spec is the contract, and the slide is the one-screen summary.

The sequence

  1. 01
    Open

    The footer link goes to /testimonials#share, or the CTA on /testimonials is pressed. The page is a prerendered shell; the chat’s code loads only now, and opening it starts nothing.

  2. 02

    The #share opener or the CTA mounts the chat island, ready to use: a written greeting and the photo widget, no second click.

  3. 03
    Talk

    The first photo or message posts to /api/testimonials/chat. BotID and the Firewall rule (per IP) check it; the route starts one workflow run bound to the session id. Every later message or widget answer goes to …/message, which resumes the run’s turn hook.

  4. 04

    Each turn, WorkflowAgent streams text and widgets; the draft travels on a second stream the routes merge in. After a reload, the stream route reconnects and the messages come back from the session store.

  5. 05
    Photo

    The photo widget downsizes and re-encodes the photo in the browser (EXIF gone), asks the upload route for a token, then uploads straight to the private Blob store.

  6. 06

    analysePhoto reads the blob and asks a vision model through AI Gateway: quality, safety, is the white triangle visible, which product. The visitor confirms it or picks another.

  7. 07
    Verify

    The address goes into the draft beside the model, not through it. sendCode emails a 6-digit code through Resend; verifyCode checks it. The model only learns “verified”.

  8. 08
    Submit

    submit reads the draft, never the model’s arguments, and writes testimonialSubmission.<id>, private because its id has a dot.

  9. 09
    Wait

    The run waits on the hook testimonial-review:<runId>. Waiting costs nothing and has no time limit.

  10. 10
    Review

    The editor opens the submission in the Studio. The photo is shown through a signed store URL that streams it from Blob; nothing unmoderated is uploaded to Sanity.

  11. 11

    Accept or Reject patches status. The submission-decided Function reacts to that change.

  12. 12

    The Function posts to the decision route with a bearer secret; the route resumes the waiting run. The editor’s alt text travels with the decision.

  13. 13
    Publish

    Accepted: the run copies the photo into Sanity assets and creates testimonial-<id> with consent on record.

  14. 14

    The existing GROQ webhook calls the revalidate route, which drops sanity:testimonial: the wall, the product page and the favourites update without a deploy.

  15. 15
    Close

    Either way the run sends the outcome email, deletes the blobs and removes the email address from the submission.

Boundaries

The model proposes, code decides

  • The draft changes only through tool results.
  • submit reads the draft, never the model’s arguments.
  • Visitor text, the photo and text in it are data, never instructions.

Nothing unmoderated is public

  • Photo in private Blob until Accept.
  • The email never passes through the model.
  • Submission id has a dot: unreadable without a token.
  • EXIF removed in the browser before upload.

Secrets stay on the server

  • SANITY_API_WRITE_TOKEN, RESEND_API_KEY; Blob over OIDC
  • TESTIMONIAL_PHOTO_SECRET, TESTIMONIAL_DECISION_SECRET
  • The Function’s copy set with sanity functions env add.

Abuse is bounded

  • BotID Basic and one Firewall rate-limit rule, keyed on IP.
  • 20 turns and 2 photo uploads per run.
  • Email verified by code before submit.

Production only

  • The agent runs where the write token is set.
  • Previews show the page without the CTA.
