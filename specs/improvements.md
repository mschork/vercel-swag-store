# Improvements

Ideas deliberately left out of the release. Each entry names the decision it comes from so the trade-off is traceable. Nothing here is scheduled. Cart latency used to sit here; it is now specified in `specs/E16-cart-api-improvements.md`, built before E11.

## Home page

- **Art-directed hero image** (E04 Q1, E10). The hero photo is authored in Sanity (`homePage.hero.image`) and loads over its low-quality placeholder; without one the hero renders as words alone. The image builder applies the editor's hotspot only when it crops to fixed dimensions, and the full-bleed hero asks for a width alone, so its framing comes from a fixed `object-position` per breakpoint. What remains: derive that position from the hotspot, per breakpoint.
- **Testimonials on the home page** (E08/E09 grilling). Testimonials have their own wall at `/testimonials`, and the home page's favourites row shows the products they name. An editor-ordered section array on `homePage` would let the testimonials themselves lead the home page; it is one query and one component on top of the same schema, plus a second layout system to test.

## Product listing, search and product page

- **Price-range filter on the product listing** (E18 Q1). The API filters by category, search text and the featured flag, not by price, so a range means filtering the cached catalogue in memory. That part is cheap. What is not: two more pieces of URL state on pages that are otherwise fully prerendered, and a range control, which done well is a slider and so a client component outside the shadcn set the specs allow. In a catalogue this small a price range saves the shopper almost no scanning; the price sort gives most of the benefit with one select.
- **Sort in the URL** (E18 Q7). The listing's sort lives in component state so every listing page stays prerendered. A `?sort=` param would make a sorted view shareable and work without JavaScript, at the cost of turning each grid into a dynamic hole.
- **Editorial synonyms per category** (E07 review). `expandQuery` reaches a category from its slug and name, singular or plural, across hyphens and spaces, so "tshirt" finds the shirt. Nothing reaches a word that names no category: "tee" works only because the API happens to carry it as a tag, and a typo works never. A `searchTerms` array on the category document in Sanity would cover both without a deploy, and E13 already turns zero-result queries into the documents a human would edit: its analysis marks a gap `matched` and names the category or product it meant, which is a ready-made list of synonyms to accept.
- **Shop the look on the search page** (search in the browser, 26 Sep 2026). With nothing searched, the search page shows five featured products under their own heading, pushed down by any results. The testimonials are a better starting point: each is a photo of a person with one to three products and a quote, and a photo reads as inspiration where a grid of cards reads as results. It needs a query, a component and a layout of its own, and a decision on weight: photos cost more than product cards on a page that is otherwise almost all text. The copy may say "Shop the look"; the model keeps calling them testimonials (CONTEXT.md).
- **More in this category on the product page** (E10). On desktop the column under the buy row is empty. A strip of grid cards from the same category, from the cached category fetch, would fill it and give the page a second exit; it needs a rule for which products to show and how many, and a decision on whether it also appears on phones.
- **Product badges** (E09 follow-up, 18 Sep 2026). The product document offered New, Limited and Staff pick, shown over the photo on the product page only. Badges earn their keep while scanning a grid, and the grids read the API alone, so the label was visible exactly where the shopper no longer needed it. The API has nothing to derive them from either: every product shares one `createdAt`, and stock is random per request. Bringing them back means a cached query for the whole set, a prop on the card and a decision about how many fit.

## Cart and promotion

- **Toast notifications** (E05 Q6). Add to Cart confirms inline on the product page, and the quick-add row on the cart page confirms with a saving row. A toast (`sonner`) would confirm from anywhere, for example a quick-add on the product cards.
- **Emptying the API cart on order** (E06). Placing the demo order forgets the cart mirror, and with it the cart token; the lines stay in the API cart, which expires on its own after 24 hours without a change. The API has no clear-cart endpoint, so really emptying it would take one `DELETE` per line before the redirect: extra latency for a cart nobody holds a token for any more.
- **Promo banner rendering rules** (E04 Q6). The banner renders every field the API returns: title, description, discount percent and code. One of the four promos has `discountPercent: 0` and `code: "AUTO"`, so it reads "0% off, code AUTO". A display rule (hide the percent when zero, hide the code when the description says none is needed) would need agreement on what the API means by those values.
- **Copy-to-clipboard on the promo code** (E04 Q8). The promo banner is server-rendered text in the shell. A copy button needs a small client leaf.

## Site chrome

- **Cookie banner**. The browser holds one cookie, the session id, and it is strictly necessary for the cart to work, so consent is not legally required in most jurisdictions. A short notice would still make the behaviour transparent.
- **Icons for footer social links** (E03 Q3). The footer renders the social links as text, from `siteSettings` or the API's `socialLinks`. Icons would need one inline SVG per known network plus a text fallback for unknown keys; add them once the set of networks is stable.

## Content in Sanity

- **Editorial copy is placeholder** (E04 Q2, E08). The hero's headline and paragraph, written during E04 so the page ships (`HERO_FALLBACK`, editable in the `homePage` document), and the editorial content the seed writes were written to demonstrate the model, not to sell anything. Both deserve a proper pass before anyone treats the store as real.
- **Collections and guides in Sanity** (E08/E09 grilling, 18 Sep 2026). The content model keeps products, categories, testimonials and FAQs. Collections repeat what the API's categories and the search page already do; guides would add a second content-driven route, images and a product-embed block to the Portable Text config. Both are the same mechanisms the shipped types already demonstrate, at the cost of a schema, a query, a renderer, a fallback and a test each.
- **The revalidation webhook as a Blueprint resource** (E13). The E09 publish webhook is registered by hand in Sanity Manage. `sanity.blueprint.ts` declares the Functions, and `defineDocumentWebhook` could declare the webhook beside them, with its secret read from the environment at deploy time. Left out because it re-creates a working production webhook for no visible gain.

## Search-gap loop

- **Embeddings for clustering gaps** (E13). The model groups "umbrella" and "rain umbrella" from the text alone, which is enough at this volume. `embedMany` through AI Gateway would cluster before the model sees anything and cut the prompt; worth it past a few hundred gaps per run.

## Build and dependencies

- **Browser targets to drop legacy polyfills** (E11 follow-up, 19 Sep 2026). A Lighthouse run on the production home page scored 99 for performance and still estimated about 14 KB of wasted JavaScript in one Next.js chunk: polyfills for `Array.prototype.at`, `flat`, `flatMap`, `Object.fromEntries`, `Object.hasOwn`, `String.prototype.trimStart` and `trimEnd`, all of which are Baseline in every browser this store targets. A `browserslist` entry in `apps/store/package.json` that names modern browsers only should let the build leave them out. Left out because the gain is small against a score that is already at the ceiling, and because it needs a decision on which browsers the store supports, then a before and after measurement of the chunk and a check in an older Safari. Measure in an incognito window: the same run listed several Chrome extensions under unused and unminified JavaScript, which are not the store's.
- **TypeScript 7, ESLint 10 and `@sanity/eslint-config-studio` 7** (dependency upgrades, 26 Sep 2026). Every other dependency is on its latest release; these three majors stay behind. TypeScript 7 is the native compiler, a new toolchain for `tsc`, `next typegen` and the editor rather than a version bump, and it needs its own check that type errors, typed routes and the Sanity typegen output come out the same. `@sanity/eslint-config-studio` 7 requires ESLint 10, and `eslint-config-next` has not been checked against ESLint 10 (its peer range allows it, but its plugins are untested there), so both linters move together once the Next config is known to work.
