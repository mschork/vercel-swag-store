# Improvements

Ideas deliberately left out of the submission. Each entry names the decision it comes from so the trade-off is traceable. Nothing here is scheduled. Cart latency used to sit here; it is now specified in `specs/E16-cart-api-improvements.md`, built before E11.

- **Copy-to-clipboard on the promo code** (E04 Q8). The promo banner is static text inside a Suspense hole so it stays a server component. A copy button needs a small client leaf.
- **Category browsing route** (E05 Q10). The breadcrumb category links to `/search?category=<slug>`, reusing the search page. A dedicated `/category/<slug>` route could be fully static (no `searchParams`) and offer richer category content from Sanity.
- **Cookie banner**. The cart token lives in an httpOnly cookie. It is strictly necessary for the cart to work, so consent is not legally required in most jurisdictions, but a short notice would make the behaviour transparent. Decide with the README's privacy note in E12.
- **Art-directed hero image** (E04 Q1, E10). The hero is a full-bleed lifestyle photo from `public/`; E09 makes it authorable in Sanity (`homePage.hero.image`, falling back to the file). What remains: art direction per breakpoint via Sanity hotspot and crop instead of a fixed `object-position`, a low-quality placeholder from Sanity image metadata, and a measured LCP comparison between the Sanity pipeline and the static file.
- **Toast notifications** (E05 Q6). Add-to-cart confirms inline on the product page. A toast (`sonner`) would confirm from anywhere, for example a future quick-add on product cards.
- **Icons for footer social links** (E03 Q3). The footer renders the API's `socialLinks` as text links labelled from the record key. Icons would need one inline SVG per known network plus a text fallback for unknown keys; add them once the set of networks the API returns is stable.
- **Hero copy** (E04 Q2). The headline and supporting paragraph in `HERO_FALLBACK` are placeholder marketing copy written during E04 so the page ships. They deserve a proper pass, and once E09 lands they can be edited in the `homePage` document without a deploy.
- **Promo banner rendering rules** (E04 Q6). The banner renders every field the API returns: title, description, discount percent and code. One of the four promos has `discountPercent: 0` and `code: "AUTO"`, so it reads "0% off, code AUTO". A display rule (hide the percent when zero, hide the code when the description says none is needed) would need agreement on what the API means by those values.
- **Stock-aware cart quantities** (E06). The product page limits Add to Cart to live stock, but the API enforces no stock on cart writes (quantity 999 was accepted for a product with 5 in stock) and the cart response carries no stock, so the cart page caps a line at 99 instead. Enforcing stock there would cost one live stock call per line on every render of `/cart`, plus a rule for what to show when stock drops below a line's quantity.
- **Emptying the API cart on order** (E06). Placing the demo order drops the `cart_token` cookie; the lines stay in the API cart, which expires on its own after 24 hours without a change. The API has no clear-cart endpoint, so really emptying it would take one `DELETE` per line before the redirect: extra latency for a cart no browser holds a token for any more.
- **Editorial synonyms per category** (E07 review). `expandQuery` reaches a category from its slug and name, singular or plural, across hyphens and spaces, so "tshirt" finds the shirt. Nothing reaches a word that names no category: "tee" works only because the API happens to carry it as a tag, and a typo works never. A `searchTerms` array on a category document in Sanity would cover both without a deploy, and E13 already turns zero-result queries into the documents a human would edit: its analysis marks a gap `matched` and names the category or product it meant, which is a ready-made list of synonyms to accept. Belongs with E09, once categories have documents at all.
- **More in this category on the product page** (E10). On desktop the column under the buy row is empty. A strip of grid cards from the same category, from the cached category fetch, would fill it and give the page a second exit; it needs a rule for which products to show and how many, and a decision on whether it also appears on phones.
- **Collections and guides in Sanity** (E08/E09 grilling, 18 Sep 2026). The content model keeps products, categories, lookbook entries and FAQs. Collections repeat what the API's categories and the search page already do; guides would add a second content-driven route, images and a product-embed block to the Portable Text config. Both are the same mechanisms the shipped types already demonstrate, at the cost of a schema, a query, a renderer, a fallback and a test each.
- **Lookbook on the home page** (E08/E09 grilling). Entries render on the product pages they name. An editor-ordered section array on `homePage` would let lookbook lead the home page too; it is one query and one component on top of the same schema, plus a second layout system to test.
- **Seeded editorial copy is placeholder** (E08). The two enriched products, two lookbook entries and four FAQs the seed writes are written to demonstrate the model, not to sell anything, and deserve a proper pass before anyone treats the store as real.

- **Product badges** (E09 follow-up, 18 Sep 2026). The product document offered New, Limited and Staff pick, shown over the photo on the product page only. Badges earn their keep while scanning a grid, and the grids read the API alone, so the label was visible exactly where the shopper no longer needed it. The API has nothing to derive them from either: every product shares one `createdAt`, and stock is random per request. Bringing them back means a cached query for the whole set, a prop on the card and a decision about how many fit.
- **The revalidation webhook as a Blueprint resource** (E13). The E09 publish webhook is registered by hand in Sanity Manage. E13 introduces `sanity.blueprint.ts`, and `defineDocumentWebhook` could declare the webhook beside the Functions, with its secret read from the environment at deploy time. Left out because it re-creates a working production webhook for no visible gain.
- **Embeddings for clustering gaps** (E13). The model groups "umbrella" and "rain umbrella" from the text alone, which is enough at this volume. `embedMany` through AI Gateway would cluster before the model sees anything and cut the prompt; worth it past a few hundred gaps per run.
