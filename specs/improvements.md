# Improvements

Ideas deliberately left out of the release. Each entry names the decision it comes from so the trade-off is traceable. Nothing here is scheduled. The four cart-latency entries from E06 (optimistic add, one less call per add, coalesced quantity clicks, one shared cart read) stay out of the epics and are weighed once the whole store is built.

- **Inline header search** (E03 Q4). The nav has a link to `/search` because the requirements ask for a search page. A header search box, as on vercel.store, would shorten the path to results but means a second form and a second debounce; revisit once the search page is stable.
- **Copy-to-clipboard on the promo code** (E04 Q8). The promo banner is static text inside a Suspense hole so it stays a server component. A copy button needs a small client leaf.
- **Category browsing route** (E05 Q10). The breadcrumb category links to `/search?category=<slug>`, reusing the search page. A dedicated `/category/<slug>` route could be fully static (no `searchParams`) and offer richer category content from Sanity.
- **Cookie banner**. The cart token lives in an httpOnly cookie. It is strictly necessary for the cart to work, so consent is not legally required in most jurisdictions, but a short notice would make the behaviour transparent. Decide with the README's privacy note in E12.
- **Art-directed hero image** (E04 Q1). E09 makes the hero image authorable in Sanity (`homePage.hero.image`, falling back to a product photo). What remains: art direction per breakpoint via Sanity hotspot and crop, a low-quality placeholder from Sanity image metadata, and a measured LCP comparison between the Sanity pipeline and the blob-store photo.
- **Toast notifications** (E05 Q6). Add-to-cart confirms inline on the product page. A toast (`sonner`) would confirm from anywhere, for example a future quick-add on product cards.
- **Icons for footer social links** (E03 Q3). The footer renders the API's `socialLinks` as text links labelled from the record key. Icons would need one inline SVG per known network plus a text fallback for unknown keys; add them once the set of networks the API returns is stable.
- **Hero copy** (E04 Q2). The headline, supporting paragraph and link labels in `HERO_FALLBACK` are placeholder marketing copy written during E04 so the page ships. They deserve a proper pass, and once E09 lands they can be edited in the `homePage` document without a deploy.
- **Promo banner rendering rules** (E04 Q6). The banner renders every field the API returns: title, description, discount percent and code. One of the four promos has `discountPercent: 0` and `code: "AUTO"`, so it reads "0% off, code AUTO". A display rule (hide the percent when zero, hide the code when the description says none is needed) would need agreement on what the API means by those values.
- **Stock-aware cart quantities** (E06). The product page limits Add to Cart to live stock, but the API enforces no stock on cart writes (quantity 999 was accepted for a product with 5 in stock) and the cart response carries no stock, so the cart page caps a line at 99 instead. Enforcing stock there would cost one live stock call per line on every render of `/cart`, plus a rule for what to show when stock drops below a line's quantity.
- **Emptying the API cart on order** (E06). Placing the demo order drops the `cart_token` cookie; the lines stay in the API cart, which expires on its own after 24 hours without a change. The API has no clear-cart endpoint, so really emptying it would take one `DELETE` per line before the redirect: extra latency for a cart no browser holds a token for any more.
- **Optimistic Add to Cart on the product page** (E06). The product page waits for the whole round trip before it says "Added", because the confirmation is the action's result and the count is the server's re-render. Showing both at once and reconciling when the action answers needs a client-held count in the shell that the badge reads, seeded by the server, plus a revert path for a failed add. It buys the appearance of an instant cart and costs the shell its freedom from client state.
- **One less API call per add** (E06). `addToCart` reads the cart before writing so a missing or expired cookie is replaced first. Writing first and creating a cart only when the write answers 404 would save one 1.4 to 2.0 s read on every add, at the cost of a retry path and, in the rare expired case, a second write.
- **Coalesce quantity changes** (E06). Each minus or plus click sends one `updateQuantity`, and the row ignores further clicks while one is in flight, so going from 1 to 5 is four sequential waits of about two seconds. The API takes an absolute quantity, so the row could keep accepting clicks, move optimistically and send only the last value after a short pause, last write wins. The trade-off is a timer per row and a rule for a page left before it fires.
- **Share one cart read per request** (E06). On `/cart` the badge and the contents each call `GET /cart`: `fetchApi` gives every request an abort signal for its five-second timeout, and a request carrying a signal opts out of Next's per-render fetch memoization. The two reads run in parallel, so the page is no slower, but the API does twice the slow work. Wrapping `getCartFromCookie` in React's `cache()` would dedupe them per request and leave the timeout as it is.
