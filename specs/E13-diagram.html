E13 Search-gap loop

A search that finds nothing is counted after the page has been sent. When the same thing is missed often enough, a model groups the misses into product ideas, and a person accepts or rejects each idea in the Studio. Nothing here touches the catalogue or slows a page. This page is the picture; the spec is the contract.

The loop at a glance

Step by step

  1. StoreE07, unchanged

    A visitor searches

    The search form navigates to /search?q=… on Enter, on the button, and after a 300 ms pause in typing from three characters on. All three are the same navigation, so the server cannot tell a finished search from a pause.

  2. StoreSlice 2

    The search finds nothing

    SearchResults records a miss only when all three hold:

    • there is a query,
    • no category filter is set,
    • the API and the category expansion returned no product.

    The empty state says: "We keep track of what people look for and don't find."

  3. StoreSlice 2

    Should this miss be recorded at all?

    recordGapAfterResponse checks, in order. Any "no" and nothing is recorded:

    • Is SANITY_API_WRITE_TOKEN set? Previews, CI and forks have none.
    • Is the user agent a person, not a bot?
    • Does the query survive normaliseGap? See the filter table below.

    Then it registers the write with after(), so the visitor never waits for it.

  4. StoreSanity datasetSlice 2

    After the response: count the gap

    One read, at most one write. No write when:

    • the gap was counted less than 10 minutes ago, by anyone,
    • the gap is new and 500 gaps are already open,
    • the gap's status is ignored.

    Otherwise one transaction creates searchGap.<hash> if needed and adds one to count. Every failure is caught and logged as a code. The query and the token are never logged.

  5. Sanity FunctionSlice 4

    gap-threshold notices the gap matters

    Fires on every update where the gap is new, its count is 2 or more, and the count just changed. It writes nothing. It only calls the store: POST /api/demand/analyse with the bearer secret. A lost call heals itself on the next search.

  6. StoreSlice 3

    The route starts the workflow

    Wrong or missing secret: 401. Right secret: it starts analyseDemand and answers 202 at once. The same call by hand with {"settle": false} skips the wait in step 8.

  7. Vercel WorkflowSlice 3

    Lock: only one run at a time

    The run claims the hook token demand-analysis. If another run holds it, this one ends as skipped. A burst of Function calls collapses into one analysis.

  8. Vercel WorkflowSlice 3

    Settle for ten minutes

    A durable sleep. It lets "umbrellas" and "rain umbrella" arrive next to "umbrella", and lets someone finish typing.

  9. Vercel WorkflowSanity datasetSlice 3

    Step claim

    • Delete gaps that stayed under 2 searches and went quiet for 30 days.
    • Take up to 100 gaps that are new with a count of 2 or more.
    • Typing fragments of those gaps go to ignored with a note.
    • The rest go to analysing under this run's id. Each patch is guarded by the revision that was read.

    Nothing claimed: the run ends here.

  10. Vercel WorkflowStore's cached API readersSlice 3

    Step catalogue

    Every product and category from the Swag Store API, through the same cached functions the pages use. This is what "already sold" is judged against.

  11. Vercel WorkflowModelSlice 3

    Step propose: the one model call

    The model gets the categories, the products and the gaps as a JSON array. It has no tools and must answer in one schema: clusters, each of kind newProduct, alreadySold or noise. The queries are presented as untrusted data, never as instructions. A malformed answer throws and the step retries.

  12. Vercel WorkflowSlice 3

    Validate: nothing the model says is written unchecked

    • Gap ids that were not claimed are dropped, and so is a gap's second appearance.
    • An idea named like an existing product is dropped.
    • A category or match that is not a real slug is cleared. "Already sold" without a real match becomes noise.
    • Claimed gaps that no cluster mentions are listed to go back to new.
  13. Vercel WorkflowSanity datasetSlice 3

    Step write: one transaction

    • newProduct: create productIdea.<hash> as proposed, with the summed demand. Its gaps become reviewed.
    • alreadySold: gaps become matched, with the match and the reason as a note.
    • noise: gaps become ignored, with the reason.
    • Unmentioned gaps return to new.

    The idea's id is a hash of its gap ids, so a second run over the same gaps creates nothing new.

    If anything throws after the claim, step release puts this run's gaps back to new and the run shows as failed. No gap is ever stuck in analysing.

  14. Sanity FunctionSlice 5

    idea-start-review opens a review

    Fires when a productIdea is created and starts a Sanity Workflows instance of idea-review for it.

  15. EditorSlice 5

    A person decides

    In the Studio, under "Demand signals", the editor opens the idea and chooses Accept, or Reject with a reason. Without slice 5 the same decision is a radio field on the idea.

  16. Sanity FunctionSanity datasetSlice 5

    wf-drain-effects applies the decision

    • Accepted: the idea becomes accepted and its gaps promoted.
    • Rejected: the idea becomes rejected with the reason, and its gaps stay reviewed.

    Delivery is at least once, so a decision already on the idea writes nothing. wf-heartbeat runs daily to sweep stale work.

    The loop ends here. "Accepted" is a signal to whoever owns the catalogue. The API has no way to create a product, and nothing downstream trusts the flag.

What a gap and an idea can be

Search gap

new→ analysing→ reviewed→ promoted

From analysing a gap can also become matched (we sell it under another word), ignored (noise or a typing fragment), or return to new (the model skipped it, or the run failed). An ignored gap stops counting. Every other settled gap keeps counting without changing status.
